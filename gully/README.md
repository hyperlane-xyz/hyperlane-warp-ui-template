# Gully Bridge (testnet)

One bridge app for GullyChain Testnet (485590) and every chain of the multi-chain manifest: Arbitrum Sepolia (421614),
Ethereum Sepolia (11155111), Base Sepolia (84532), BNB Chain Testnet (97) and Solana Devnet (Hyperlane domain
1399811151), both ways ("From any chain -> Gully Chain" and back). With Arbitrum Sepolia there are two lanes:

| Lane | What it uses | Time | You get |
|---|---|---|---|
| **Fast** | Hyperlane native ETH warp route (2-of-3 Gully validators, Gully relayer) | about a minute, both ways | native gas ETH on GullyChain, ETH back on Arbitrum Sepolia (up to each router's liquidity) |
| **Canonical** | GullyChain's Arbitrum Nitro rollup bridge (Inbox, ArbSys, Outbox) | deposits about a minute; withdrawals take the challenge period, then a claim | native gas ETH |

The app suggests a lane for each amount and direction (`src/bridge/selectRoute.ts`, unit-tested), and the user can switch.
In the UI the lanes are called **Fast** and **Cheapest**, with time and fee in plain words (`src/bridge/laneCopy.ts`).
Every other chain has one lane, Fast (Hyperlane warp routes, our validators), and the card says so.
It is to replace the canonical-only bridge at testnet-bridge.gullychain.xyz.

## Multi-chain routes

The single source of truth is gully-ops `l3/hyperlane/multichain/routes.yaml` (block `testnet`; `mainnet` has the same
shape). `npm run routes` reads it next to the registry and writes every route into `routes.json` (`multichain`, plus
`chains`): ETH (Sepolia, Base Sepolia native ETH, BSC test ETH -> gas ETH on Gully), USDC (EVM origins incl. Arbitrum
Sepolia -> USDC.e on Gully), USDT and BNB (-> synthetic on Gully), SOL (native SOL -> synthetic SOL, 9 decimals) and
USDC-SOL (Solana USDC -> USDC.e). Router addresses come from `deployments/warp_routes/<route id>-config.yaml`, which the
Hyperlane CLI writes after the owner deploys (EVM and Sealevel: `SealevelHypNative` / `SealevelHypCollateral`, base58).
Until a route's config exists its tokens have `"address": null`: the chain and token pickers show it as **Coming soon**
(visible, not sendable). Re-run `npm run routes` after each deploy; the live classic routes are unchanged.

- **Gas on arrival.** A wallet's first deposit of a non-ETH token gets a small ETH drop on Gully from `GullyGasDrop`
  (gully-ops). The card shows it when `dropped(recipient)` is false and `remainingToday() >= dropAmount()`, and the
  transfer's status shows "Gas drop on the way / received". Off until `VITE_GAS_DROP_ADDRESS` is set at build time.
  Gully ID passkey smart accounts (Kernel) get "the Gully paymaster pays your gas" instead.
- **Solana.** Wallets through the Wallet Standard (`standard:connect` + `solana:signAndSendTransaction`: Phantom,
  Solflare...). `@wallet-standard/app` and `@solana/web3.js` are lazy chunks, loaded only when a Solana route is used.
  The TransferRemote builder (native + collateral, IGP / overhead IGP) mirrors `@hyperlane-xyz/sdk` 45.0.1 and was
  checked against it account by account. Routes with a warp fee or the IGP's new offchain-quote flow are refused.
- **Status.** Message id from the origin receipt (`DispatchId` on the origin Mailbox; Solana: the mailbox's
  "Dispatched message to <domain>, ID <id>" log), delivery = `Mailbox.delivered(id)` (Solana: the processed-message
  PDA), delivery tx = the destination Mailbox's `ProcessId(id)`. Steps: Sent, Verified by validators, Delivered, with
  the origin and delivery tx links and, under Details, the Hyperlane Explorer link.
- **History.** `localStorage['gully-bridge:transfers']`, same key as before; older entries are migrated on load
  (`src/bridge/history.ts`).
- URL: `?chain=sepolia|basesepolia|bsctestnet|solanadevnet` and `?token=USDC` preselect a chain and token.

## Why a separate app in this fork

Since v3 ("Engine-Owned Transfers"), the upstream template sends every transfer through Hyperlane's hosted Universal
Router API. That API does not know chain 485590 or our routes, and the template needs a Next server. This folder is a
static Vite + React + viem app that calls the warp routers and the rollup bridge directly. It shares no code with the
template, and the template stays untouched for future upstream merges.

## Integrators

- `?ref=0x…`: the integrator address. It is kept for the session, shown on the quote and passed as `req.ref` to the bridge client.
- `?embed=1` or `/embed`: the card only, transparent background. It posts `{type:'gully-bridge', event:{type:'ready'}}` to the parent window.
- Other query parameters: `direction=deposit|withdraw`, `route=fast|canonical`, `amount=0.01`.

## Sign in with Gully ID (on by default)

The header shows the official "Sign in with Gully ID" button, drawn by the Gully ID SDK (`src/gully-id/`; dark, size
S; on screens up to 900 px it sits in the menu with the passkey option, never clipped). Client `gully-bridge`, issuer
`https://gullyid.xyz`; the SDK loads lazily from `/sdk/v1.js`, falling back to `/sdk.js`. It shows the user's .gully
name and avatar, plus their Gully ID wallet address when the profile has one. It is identity only: transfers are still
signed by the wallet connected with Connect, and nothing is auto-connected. If the SDK fails to load the button simply
does not appear. `<html data-gully-id="on|off">` shows the flag state. Needs the CSP in `deploy/Caddyfile.bridge`
(gullyid.xyz in script-src and connect-src, https: in img-src).

```sh
node scripts/build-staging.mjs <out>                          # on (client gully-bridge)
VITE_GULLY_ID_SIGNIN=off node scripts/build-staging.mjs <out>  # rollback: no button, the SDK is never requested
```

`VITE_GULLY_ID_CLIENT_ID` / `VITE_GULLY_ID_ISSUER` override the defaults.

## Gully Warp Mirrors (coin routes from /mirrors.json)

At startup the app fetches same-origin `/mirrors.json` (published every minute by the relayer sync on gully-l3, gully-ops
`l3/hyperlane/agents/sync-mirrors.mjs`, schema `gully-warp-mirrors/1`) and adds one Fast route per active, relayed
Gully Core coin mirror on a chain the app knows (testnet: Arbitrum Sepolia): `MIRROR/<originToken>/<chainKey>`, GullyChain
side = the GullyCollateral (`EvmHypCollateral`, `collateralAddress` = the coin, approve first), destination side = the
GullyMirror (`EvmHypSynthetic`). They live in `MIRROR_ROUTES` (`src/config/routes.ts`), separate from the ETH routes, so
the default ETH route, stats and the activity feed are unchanged; no file or a fetch error simply means no mirror routes.

- The card shows an Asset picker (ETH + every mirror) and, on a mirror, "Trading on <chain> · Launched on Gully Chain ·
  Liquidity on Gully Core" with links to the mirror on the destination explorer (provenance), the coin page (kre8.fun/drop/<coin>) and
  Powered by Gully Core. Mirror routes are Fast only (the canonical bridge carries ETH only).
- Deep link `?token=<originToken>&to=<domain|chainKey>` (kre8.fun Drop page): preselects that mirror, direction
  GullyChain -> destination; when the connected wallet holds the mirror the default flips to **Bridge back**
  (destination -> GullyChain) unless the link set `direction=`.
- While the relayer is restarting on a new whitelist (`pendingRelayerRestart`), quotes are unavailable ("syncing").
- Tests: `src/config/mirrors.test.ts` (route mapping, registry, deep-link parser).

## Commands

```sh
npm install
npm run brand            # copy GullyChain kit v4 (icon, dark badge), GN 2.0 favicons + OG card from gully-ops, + Gully Labs dark badge (byte for byte)
npm run night            # re-vendor Gully Chain Night from a gully-ops checkout: npm run night -- ../../gully-ops <commit>
npm run routes -- ../../gully-ops/l3/hyperlane/registry   # + ../multichain/routes.yaml (testnet; --network mainnet)
npm run dev              # VITE_DIRECTION=a|b|c; GullyChain RPC is proxied to the SSH tunnel (127.0.0.1:18545)
npm test                 # unit tests
node tests/simulate.mjs  # every transfer path as eth_call against the live contracts, from a throwaway address
BASE=http://127.0.0.1:5234/ CHROME=<chrome.exe> node tests/e2e.mjs   # Playwright 375/768/1280/1920
node scripts/build-staging.mjs <out>   # production static build (direction C, production RPCs)
```

Deploy: `sh scripts/deploy-l3.sh <stagedDir>` uploads to `/srv/status/sites/testnet-bridge.gullychain.xyz.new` on
gully-l3, copies the live `assets/` into it without overwriting (`cp -rn`, so open tabs keep finding their old lazy
chunks), swaps live -> `.old` and `.new` -> live, then checks the page and every JS chunk on both hostnames. The Caddy
block (`deploy/Caddyfile.bridge`) lives in `gully-ops/l3/edge/Caddyfile.l3.tpl`.

## Notes

- Canonical withdrawals can only be claimed after the rollup confirms an assertion that includes them. As of
  2026-10-26 `latestConfirmed()` is still the genesis assertion, so the UI shows "Waiting for the first confirmed
  rollup assertion" until the BoLD validator posts and confirms one.
- Canonical deposit delivery times are not plotted: the GullyChain block that reads a deposit carries the deposit's
  own timestamp, so the chain cannot measure the delay.
- The CSP in `deploy/Caddyfile.bridge` allows the multi-chain RPCs; gully-ops `l3/edge/Caddyfile.l3.tpl` needs the same
  `connect-src` before the multi-chain build goes live.
- Attribution: the footer says "Fast lane secured by Hyperlane". The Hyperlane contracts and agents are Apache-2.0;
  this app has no Hyperlane UI code.
